# Проверка и сдача

Пакет готовит интегратор. Пока четыре рабочих модуля не подключены и реальные переводы не проверены носителем, интеграционный комплект нельзя сдавать как завершённый продукт.

## Обязательные результаты кейса

- Работающий CLI `locqa check --source … --target … --glossary … --out …`.
- `report.json` в формате брифа и человекочитаемый HTML-отчёт.
- `glossary.csv` с колонками `ru,kk,en,comment`.
- `intl_kk_fixed.arb` с отметками человеческой проверки у изменённых строк.
- Методология: как искали, исправляли и проверяли, сколько строк прочитал носитель.
- Инструкция воспроизводимого запуска и необходимые зависимости.

Журнал reviews, показатели, протокол нормализации и журнал Flutter приложите как доказательства. Их наличие не заменяет обязательные результаты.

## Локальная структура

```text
data/          исходные файлы организаторов; не редактировать
private/       разметка, решения носителей, протокол нормализации
outputs/       промежуточные отчёты и результаты
submission/    финальный пакет для организаторов
```

Эти каталоги игнорируются Git. Перед коммитом дополнительно проверьте `git status` и `git diff --cached`. Не публикуйте пакет с реальными данными в GitHub Releases или публичных артефактах CI.

## Проверки перед упаковкой

1. Запустите `npm test` и `npm run check`.
2. Зафиксируйте версию входов, модели, глоссария и кода.
3. Убедитесь, что каждая применённая замена имеет актуальное человеческое решение и отметку в метаданных ARB.
4. Разберите конфликтующие дубли. Сохраните исходный файл, хэш, выбранные вхождения и обоснование нормализации. Молчаливое сведение к последнему значению недопустимо.
5. Выполните независимую проверку пакета:

```sh
npm run release-check -- --source data/intl_ru.arb --original-target data/intl_kk.arb --fixed submission/intl_kk_fixed.arb --report submission/report.json --reviews private/reviews.json --glossary submission/glossary.csv --html submission/report.html --methodology submission/methodology.md --out outputs/release-check.json
```

Пути приведены как локальный пример. Если исходники требуют нормализации, сначала согласуйте и задокументируйте её с владельцем ядра. Не подменяйте baseline только ради обхода проверки.

6. Выполните **реальную** проверку Flutter на финальных файлах:

```sh
npm run flutter-smoke -- --source data/intl_ru.arb --target submission/intl_kk_fixed.arb --out work/flutter-final
```

Успех `release-check` не означает успех `flutter gen-l10n`. Каждый Flutter-прогон требует новый конечный каталог `--out`; предыдущий результат не перезаписывается. Сохраняйте `flutter.log` и `evidence.json` с фактическим статусом и кодами команд. Приложите журналы обеих проверок. Если исходный source несовместим со Flutter, зафиксируйте это отдельно и решите совместимость явно.

Локальная синтетическая проверка Flutter и упаковки проходит. Проверка исходной выгрузки отдельно обнаружила недопустимые Flutter resource names ещё до исправлений команды. Оригиналы сохранены; нормализацию ключей необходимо согласовать, сохранив соответствие исходным ключам для интеграции и оценки. Успех на синтетике не заменяет проверку финальных source/fixed.

7. Запустите проект из чистой копии по инструкции. Убедитесь, что для получения обязательных результатов не нужны незаписанные ручные действия.
8. Проверьте пакет и отправьте организаторам. Последние три часа плана оставлены для этого этапа.

## Честная демонстрация

Покажите найденную проблему, объяснение, действие носителя, экспорт и успешный Flutter-прогон. Для демонстрации без сети можно использовать сохранённые реальные результаты, обозначив их как сохранённый запуск. Синтетический `npm run demo` обозначайте как проверку интеграционного комплекта.
