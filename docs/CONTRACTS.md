# Контракты v1

Машиночитаемый источник истины — JSON Schema в `contracts/`; дополнительные проверки хэшей находятся в `src/contracts.mjs`. Формат UTF-8, JSON без комментариев. У каждого запуска одна целевая локаль. Несовместимое изменение схемы согласуется с интегратором.

## 1. Нормализованные записи — bundle

Корневые поля: `schema_version: "1.0"`, `source_locale`, `target_locale`, `entries`.

Каждая запись содержит:

| Поле | Значение |
|---|---|
| `entry_id` | `encodeURIComponent(key) + "#" + occurrence` |
| `key` | Исходное имя ARB-ключа |
| `occurrence` | Номер целевого вхождения с 1; 0, если ключ отсутствует |
| `source` | Текст исходного языка |
| `target` | Строка или `null` для отсутствующего ключа |
| `source_hash` | SHA-256 точного `source` в UTF-8 |
| `target_hash` | SHA-256 точного `target`; `null`, если перевода нет |
| `context` | Объект с необязательными `section`, `description`, `references` |

`references` — словарь дополнительных переводов по локали, например `en` и `uz`. Отсутствие перевода (`null`) отличается от существующей пустой строки (`""`). Хэши вычисляются без trim, нормализации Unicode или изменения переносов. Функция `hashText` доступна из `src/contracts.mjs`.

Одинаковые `entry_id` запрещены. Повторяющиеся ключи не должны исчезать при чтении. Если исходный ключ имеет разные значения, привязку исходного текста нужно разрешить явно до языкового анализа и исправления.

## 2. Находки — report

`report.json` — массив объектов с девятью обязательными полями:

| Поле | Требование |
|---|---|
| `key` | Непустая строка |
| `issue_type` | Один из 11 кодов ниже |
| `severity` | `high`, `medium` или `low` |
| `source`, `target` | Строки; в официальном отчёте отсутствующий target представлен `""` |
| `evidence` | Непустое конкретное объяснение |
| `suggestion` | Строка; `""`, если безопасного предложения нет |
| `confidence` | Число от 0 до 1 |
| `reviewed_by_human` | Boolean; для машинных находок сначала `false` |

Коды: `untranslated`, `same_as_source`, `placeholder_mismatch`, `plural_mismatch`, `glossary_violation`, `length_overflow`, `machine_translation_suspect`, `inconsistent_term`, `suffix_harmony`, `orthography`, `wrong_language`.

Новые поля в этом формате не добавляются. Идентификаторы вхождений, трассировка модели, метрики, структурные ошибки и дубли хранятся в отдельных служебных файлах. Официальный формат не различает вхождения одного ключа: перед экспортом неоднозначные дубли необходимо разрешить, сохранив внутреннюю трассировку.

Локальная оценка сопоставляет пару `(key, issue_type)`. Совпадение ключа при неправильном типе не считается верным ответом. Для разных локалей запускайте оценку отдельно.

`confidence` отражает уверенность алгоритма; без калибровки это не вероятность правильности. Флаг в находке не заменяет решение человека об исправлении. Автоматический экспорт не должен считать любое `reviewed_by_human: true` разрешением поменять строку.

## 3. Решения человека — reviews

Корневые поля: `schema_version: "1.0"`, `target_locale`, `decisions`.

Каждое решение содержит `key`, `entry_id`, `decision`, `original_text`, `approved_text`, `source_hash`, `original_hash`, `approved_hash`, `reviewer`, `reviewed_at`, `reviewed_by_human: true`.

- `accepted`: человек принял предложенную версию.
- `edited`: человек написал или изменил версию и одобрил её.
- `rejected`: предложение отклонено; `approved_text` и `approved_hash` равны `null`.
- `original_text` и `original_hash` равны `null` только для отсутствующего перевода.
- `reviewed_at` — дата-время ISO 8601 с часовым поясом.
- На одно `entry_id` в текущем наборе допускается одно решение. История хранится отдельно.

Хэши должны соответствовать точным текстам. Перед применением решения экспорт проверяет также текущий source и original target. Изменение любого из трёх текстов делает прежнее одобрение неприменимым. Валидатор проверяет внутреннюю согласованность записи, но не может удостоверить личность проверившего или факт реального чтения.

Интерфейс может держать незавершённые предложения в своём рабочем формате. В `reviews` попадают только завершённые человеческие решения; пустой журнал допустим.

## 4. Отметка в исправленном ARB

У изменённого ключа сохраняются существующие метаданные `@key`. В них добавляется объект `x-locqa` с полями:

```text
reviewed_by_human, reviewer, reviewed_at,
source_hash, original_hash, approved_hash
```

Значения должны совпадать с применённым решением. Техническую совместимость такой записи проверяют реальным `flutter gen-l10n`. Отдельный журнал решений сохраняется вместе с методологией. Агент не создаёт реальные одобрения от имени человека.

## 5. Дубли и структурные дефекты

Повторяющийся `@@comment` — служебный разделитель, его нельзя смешивать с текстовыми ключами. Обычные дубли требуют отдельной диагностики:

- При одинаковых значениях возможно документированное устранение повторов с сохранением эффективного текста и контекста.
- Различающиеся значения блокируют безопасный выпуск до явного решения.
- Сохраняйте исходный файл, его хэш, все вхождения и запись о выборе значения.
- Не обходите блокировку, молча заменив исходный baseline очищенным файлом.

Процедуру нормализации конфликтующих исходников согласуют Дамир и интегратор. Она должна быть воспроизводимой и отражённой в методологии. `duplicate_key` не является дополнительным конкурсным `issue_type`.

## 6. Слияние и передача модулей

Дамир и Бекзат передают отдельные report-массивы. Полностью одинаковые находки можно объединить. Различающиеся сведения для одной пары ключ/тип должны быть разобраны; нельзя молча выбрать более высокий confidence и потерять другое предложение.

Тони принимает report вместе с bundle и отдаёт reviews. Дамир экспортирует исправленный ARB только из применимых одобрений. Интегратор проверяет итог независимо. Проход проверки схемы означает правильность формата, а не правильность перевода.
