# Методология оценки

Этот файл задаёт процесс и форму отчёта. Он не содержит измеренного качества команды, результатов носительской проверки или стоимости реальной обработки. Заполненный отчёт с данными хранится вне публичного Git.

## Разделение наборов

1. Публичные синтетические примеры проверяют схемы, отрицательные случаи и арифметику метрик. Они известны разработчикам и не служат независимой оценкой качества.
2. Отдельный локальный размеченный набор фиксируется до финальной настройки. Храните его вне Git, с версией и хэшем. Автор детектора не должен подстраивать решение под финальную разметку.
3. Скрытая разметка организаторов недоступна. Recall по ней до судейской оценки неизвестен.

Не переносите реальные выгрузки или производные фрагменты в публичные fixtures. Синтетические лингвистические примеры требуют проверки носителем перед применением как авторитетного эталона языка.

## Детекция

Единица сопоставления — пара `(key, issue_type)` для одной целевой локали. Повторы одной пары не увеличивают число найденных ошибок. Неверный тип создаёт ложную находку и пропуск ожидаемого типа.

```text
precision = TP / (TP + FP)
recall    = TP / (TP + FN)
F1        = 2*TP / (2*TP + FP + FN)
```

При отсутствии соответствующего знаменателя значение не определено: используйте `null`, а не придуманную 100% точность. Сохраняйте абсолютные TP/FP/FN, показатели по типам и дубли. Команда `evaluate` помечает результат как оценку локального размеченного набора.

Для оценки реального отчёта после фиксации версии выбирайте до 100 уникальных находок воспроизводимой выборкой:

```sh
npm run sample-review -- --report outputs/report.json --out private/precision-sample.json --size 100 --seed final-v1
```

Человек проверяет обоснованность находки **и правильность типа**. Непроверенные строки остаются пустыми; сомнения не превращаются автоматически в подтверждение. Итог формулируется, например, как «подтверждено X из Y проверенных; выбрано N; остальные ожидают проверки». Для общей precision используйте репрезентативную выборку всего отчёта. Дополнительную выборку редких типов обозначайте отдельно.

Результаты без разметки нельзя автоматически считать ложными, если gold не является исчерпывающей разметкой всего оцениваемого набора. Перед оценкой фиксируйте охват gold.

## Качество исправлений

Решение о выпуске принимает носитель казахского. Сохраняйте точный текст, проверившего, время и хэши. После редактирования текста одобрение требуется повторно. Флаг в JSON не доказывает сам факт человеческой проверки.

Для независимой оценки дайте другому носителю исходный и исправленный варианты в случайном порядке, без указания авторства. Сохраняйте «лучше A / лучше B / равно / не могу оценить» и замечание о смысле. Раскройте порядок только после решений. Если второго носителя нет, явно укажите, что оценка не независимая.

150 изменённых строк в брифе — размер судейской выборки. Не создавайте лишние замены ради квоты. Отчитывайтесь о числе просмотренных, изменённых, одобренных и отклонённых строк отдельно.

## Техническая оценка

Проверки должны включать:

- Неизвестные заранее имена ARB-ключей и корректные отрицательные примеры.
- Пропуски и пустые переводы как разные исходные состояния.
- Повторяющиеся обычные ключи и `@@comment`.
- ICU с вложениями и экранированием; валидные отличия plural-категорий разных языков.
- Сохранение имён плейсхолдеров, форматных токенов, тегов и значимых переносов.
- Неприменимость старого решения после изменения source, original target или approved text.
- Реальный `flutter gen-l10n` на итоговых файлах.

Проверяйте исходный baseline через Flutter отдельно, чтобы отличать исходные несовместимости от внесённых командой. Успех JSON Schema или общего ICU-парсера не заменяет компиляцию Flutter.

Сравните одинаковый набор при включённых только строгих проверках и при добавлении языкового модуля. Покажите, какие новые корректные находки добавил языковой анализ и сколько возникло ложных тревог.

## Время и стоимость

В журнале обработки фиксируйте модель/версию, настройки, число запросов, входные и выходные токены, попадания в кэш, ошибки и повторы, время начала/конца. Стоимость рассчитывайте по тарифу провайдера, действовавшему при запуске, с указанием валюты и даты тарифа. Сохраняйте фактические данные, а не оценки модели.

## Форма итогового отчёта

- Версия кода, параметры запуска, хэши входных файлов.
- Политика дубликатов и список выполненных нормализаций.
- Размер и происхождение локального теста, разделение настройки и проверки.
- TP/FP/FN и показатели по типам; методика ручной выборки.
- Число реальных человеческих проверок и изменённых строк.
- Результат независимого сравнения переводов или его отсутствие.
- Результат release-check и Flutter, ссылки на локальные журналы.
- Время, стоимость и известные ограничения.
