# Подключение модулей и воспроизводимый запуск

Runner запускает реальные процессы по конфигурации и проверяет каждый передаваемый файл.
Он не содержит скрытого детектора и не подменяет отсутствующий модуль тестовыми результатами.

## Конфигурация

Источник формата — `contracts/pipeline.schema.json`.
`contracts/examples/pipeline.json` подключает команды объединённых модулей.
Файлы `modules/core/normalize.mjs`, `modules/core/check.mjs`,
`modules/language/check.mjs`, `modules/report/render.mjs` и
`modules/core/export.mjs` доступны в ветке `codex/team-integration`.
Если фактические имена или аргументы отличаются, измените конфигурацию; переписывать runner не нужно.

Каждая стадия задаёт `executable` и массив `argv`. Процессы запускаются с `shell:false`.
Для Node.js используйте `executable: "node"` и путь к скрипту первым элементом `argv`.
Для Python — исполняемый файл Python и путь к адаптеру. Windows `.bat/.cmd` не исполняются
через скрытую shell-обёртку: нужен нативный executable или Node/Python-адаптер.
Конфигурация является доверенным кодом команды; runner не изолирует произвольную вредоносную программу.

`working_directory` разрешается относительно каталога файла конфигурации.
Все пути, подставляемые из входов и выходов, абсолютные. Подстановки не разделяются по пробелам
и не интерпретируются оболочкой. Разрешены только именованные токены:

| Токен | Значение |
|---|---|
| `{source}`, `{target}`, `{glossary}` | Копии входных файлов в каталоге запуска |
| `{bundle}` | Нормализованный bundle |
| `{core_report}`, `{language_report}` | Отчёты двух модулей |
| `{report}` | Объединённый отчёт |
| `{html}` | Самостоятельный HTML-отчёт |
| `{reviews}` | Копия решений человека; доступна только при `--reviews` |
| `{resolutions}` | Копия явных решений по дублям, если передан `--resolutions` |
| `{fixed}` | Исправленный ARB после экспортера |

`timeout_ms` задаётся для всего процесса или конкретной стадии; диапазон 50–600000 мс,
по умолчанию 120000 мс. При ошибке или таймауте дальнейшие стадии не запускаются.

## Производственный запуск

Выход должен находиться вне Git checkout: этого требует языковой модуль. Например,
из корня проекта используйте соседний приватный каталог и новое имя запуска:

```sh
node scripts/run-pipeline.mjs --config contracts/examples/pipeline.json --source data/intl_ru.arb --target data/intl_kk.arb --glossary private/glossary.csv --out ../locqa-private/run-001
```

Runner проходит стадии `normalize → core → language → merge → render`.
Успешный статус `analysis_passed` означает только успешную обработку и согласованность
артефактов. В этом режиме исправленный ARB не создаётся.

Для нового запуска после реальной проверки переводов:

```sh
node scripts/run-pipeline.mjs --config contracts/examples/pipeline.json --source data/intl_ru.arb --target data/intl_kk.arb --glossary private/glossary.csv --reviews private/reviews.json --out ../locqa-private/run-002
```

При наличии `--reviews` нужна стадия `export`. После неё runner независимо вызывает
`checkRelease`. Статус `export_preflight_passed` не означает, что Flutter уже проверен,
или что качество языка измерено. Даже пустой явно переданный журнал может запустить экспорт;
он не разрешает менять строки без одобрения.

Если вход содержит конфликтующие целевые дубли, передайте также
`--resolutions private/duplicate-resolutions.json`. Точные хэши исходников и выбранного
вхождения проверяются до запуска процессов; файл передаётся в независимый export preflight.
В конфигурации экспортера предусмотрено явное условное дополнение:

```json
"optional_argv": { "resolutions": ["--resolutions", "{resolutions}"] }
```

Этот блок добавляется к argv только при наличии входа resolutions. Обычные argv никогда
не удаляются и не заменяются пустыми строками автоматически. Если модуль использует другой
интерфейс, измените его optional_argv явно. Решение по дублю не заменяет одобрения нового перевода.

Для каждого запуска нужен **новый** конечный `--out`; существующий каталог не перезаписывается.
Исходники копируются байт-в-байт в `inputs/`, и адаптерам передаются именно эти копии.
Изменение копий или результатов предыдущих стадий обнаруживается по SHA-256.
Исходные пользовательские пути не передаются адаптерам в аргументах.

## Несколько наблюдений для одной строки

По умолчанию merge остаётся строгим: разные находки с одинаковыми key/type
останавливают маршрут. Опция CLI `--combine-same-text` явно включает политику
для нескольких машинных наблюдений с **одинаковыми source и target**.
Все объяснения и предложения сохраняются в evidence и `merge-audit.json`
с индексами первоначальных report-массивов. Сами отчёты модулей не меняются.
Серьёзность берётся максимальная для очереди проверки, confidence — минимальная;
если предложения различаются, итоговый suggestion пуст. Человеческое решение
не создаётся. Разные версии текста или человеческие статусы по-прежнему блокируются.

Хэш merge-audit входит в pipeline-evidence и проверяется после следующих стадий.
Общие схемы report/bundle/reviews не изменены. API: `runPipeline({ ..., combineSameText: true })`.
Это объединение наблюдений, а не разрешение дублей ARB или выбор исправления.

## Что проверяется

- Bundle соответствует схеме, точным входным текстам, хэшам и всем вхождениям ключей.
- Отсутствующий перевод представлен occurrence=0 и target=null.
- Конфликтующие исходные source-ключи требуют явного разрешения до анализа.
- Машинные отчёты соответствуют текущим строкам и не могут утверждать `reviewed_by_human=true`.
- Неодинаковые находки с одной парой key/type не сливаются молча.
- Отчёт HTML содержит самостоятельные html/body элементы.
- Результаты — обычные файлы внутри каталога запуска; ссылки и выход за каталог отклоняются.
- Экспорт при наличии журнала проходит отдельную проверку одобрений, метаданных и технической сохранности.

Официальный report не различает вхождения повторяющегося ключа. Конфликтующие
целевые дубли сохраняются в bundle, но требуют разрешения перед надёжным экспортом.
Дополнительные target-ключи, отсутствующие в source, не входят в bundle; экспортер
обязан сохранить их согласно правилам release-check.

## Протокол запуска

`pipeline-evidence.json` содержит статус, режим, исходные хэши, хэш конфигурации,
команды без shell-склейки, коды завершения, длительность стадий, хэши артефактов и журналов.
Для каждой стадии сохраняются `<stage>.stdout.log` и `<stage>.stderr.log`.
Логи ограничены последними 262144 символами текста каждого потока; факт усечения записан в evidence.

При сбое статус равен `failed`; частичные файлы сохраняются для диагностики.
Не используйте их как готовый пакет. Runner всегда оставляет `flutter_verified:false`:
Flutter и финальная упаковка выполняются отдельными проверками на тех же файлах.

## Синтетическая проверка интеграции

```sh
node scripts/run-pipeline.mjs --config fixtures/synthetic/adapters/pipeline.json --source fixtures/synthetic/source.arb --target fixtures/synthetic/target.arb --glossary fixtures/synthetic/glossary.csv --out work/pipeline-demo-001 --synthetic
```

У этого конфига `mode: "synthetic"`; без явного `--synthetic` запуск запрещён.
Его процессы действительно запускаются, но core и language читают **заранее подготовленные**
находки. Это проверка интеграции, а не измерение качества детектора.
Экспорт исправлений и одобрения человека синтетическая конфигурация не создаёт.
