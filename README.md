# Qazaq Loc QA — объединённая сборка команды

Qazaq Loc QA помогает проверять казахскую локализацию игры по русскому оригиналу:
читает ARB, находит технические и языковые риски, объясняет находки, собирает их
в HTML для редактора и экспортирует исправления по проверяемому журналу решений.

**Ссылка для жюри:** [общая ветка и этот README](https://github.com/foxfordkz-cyber/stupits-karaganda/tree/codex/team-integration).
В ней находится работа всей команды. При открытии корня репозитория GitHub может
показать другую ветку — используйте ссылку выше или выберите `codex/team-integration`.

Ветка `codex/team-integration` объединяет все опубликованные ветки на 31.10.2026.
Работают ядро ARB, локальный языковой детектор, процесс проверки Айданы,
HTML-интерфейс Тони и инструменты экспорта, Flutter-проверки и упаковки.
Объединение выполнено по поручению интегратора; исходные ветки сохранены.

**Код подготовлен к передаче. Реальный пакет локализации пока требует человеческой
проверки и решения исходных структурных проблем.** Ни объединение веток,
ни успешные тесты не создают человеческих одобрений.

## Работа всей команды

| Участник / модуль | Что реализовано | Результат в общем маршруте |
|---|---|---|
| Дамир — `modules/core/` | CLI, чтение ARB с сохранением вхождений, разделов и метаданных; структурный ICU; пять технических проверок; экспорт по актуальным человеческим решениям | Нормализованный bundle, технические находки, отдельная диагностика дублей и структуры; защищённый экспорт ARB |
| Бекзат — `modules/language/` | Шесть языковых категорий; контекст и терминология; кэш, журнал обработки и ограничения запросов; очередь проверки v2 и контроль передачи решений | Языковые находки, объяснения и кандидаты, метрики обработки, версионная очередь; стандартный запуск без модельного API |
| Айдана — `modules/linguistics/` | Черновой глоссарий из 40 терминов, редакторская политика, пакеты по 20–30 строк, проверка схем и хэшей решений | Материалы для носителя и аудит предоставленного журнала; фактическая человеческая проверка остаётся отдельным действием |
| Тони — `modules/report/` | Автономный HTML, поиск и фильтры, карточки сравнения, рабочие правки, сохранение/восстановление сессии, режим отчёта для эксперта | Отчёт и рабочая очередь; импорт существующих человеческих записей; черновик не становится одобрением автоматически |
| Интегратор — `src/`, `scripts/`, `contracts/`, `test/` | Общие схемы, последовательный запуск модулей, объединение находок, контроль хэшей, методология оценки, Flutter, проверка и упаковка | Один воспроизводимый маршрут, журналы этапов, независимая проверка выпуска и состава архива |

Поток анализа: **RU/KK ARB → Core → bundle → Core + Language → объединённый report → HTML**.
Поток исправления: **точное решение человека → аудит версий и технических ограничений →
экспорт Core → независимая проверка → Flutter → упаковка**. Второй поток доступен
в коде; тестовые решения проверяют его механику и не подтверждают реальные переводы.

## Какие проблемы ищет система

| Область | Типы находок |
|---|---|
| Техническое ядро | `untranslated`, `same_as_source`, `placeholder_mismatch`, `plural_mismatch`, `length_overflow` |
| Языковой модуль | `glossary_violation`, `machine_translation_suspect`, `inconsistent_term`, `suffix_harmony`, `orthography`, `wrong_language` |

Это 11 типов общего контракта. Дубли, неверные имена ключей и ошибки структуры
записываются отдельно. Вложенный ICU разбирается структурно; категории множественного
числа RU и KK не обязаны совпадать. При исправлении проверяются плейсхолдеры,
форматные токены, теги, переносы и специальные символы.

Языковые правила имеют ограниченную область действия: они предлагают кандидатов
для проверки. Для строгих терминологических нарушений Language нужен расширенный
согласованный JSON-глоссарий; командный CSV импортируется как черновик. Подозрение
на машинный перевод не доказывает происхождение текста, а длина не заменяет проверку
реального игрового интерфейса. [Границы языковых правил](modules/language/README.md).

## Запуск одной командой

Для жюри и другого компьютера:

```sh
git clone --branch codex/team-integration https://github.com/foxfordkz-cyber/stupits-karaganda.git qazaq-loc-qa
cd qazaq-loc-qa
npm ci
npm run verify-team
```

Если передан ZIP, распакуйте его, откройте папку `qazaq-loc-qa` и выполните
последние две команды. Клонирование и установка зависимостей требуют сети;
языковой анализ в стандартном режиме не вызывает внешний модельный API.

На этом компьютере из любой папки:

```bat
C:\stupits-karaganda-integration\verify.cmd
```

Из корня клонированной или распакованной сборки:

```sh
npm ci
npm run verify-team
```

Нужны Node.js 22+, Python 3.10+ и Flutter SDK в PATH. Дополнительных Python-пакетов
нет. Если Python установлен отдельно, задайте `LOCQA_PYTHON` полным путём к нему.
Проверены Node 24.17.0, Python 3.14.3, Flutter 3.41.2 / Dart 3.11.0.

Проверка выполняет `npm test` (включая Python suite), `npm run check`, настоящий
маршрут Core → Language → merge → HTML Тони → аудит Айданы на вымышленных данных,
экспорт через Flutter с положительными/отрицательными сценариями и упаковку.
Выход — новый каталог вне Git, его путь печатается в консоли. Можно задать его:

```sh
node scripts/verify-team.mjs --out ../locqa-private/verification-001
```

`verification.json` и отдельные логи содержат результаты. HTML для демонстрации
находится в `<каталог проверки>/team-pipeline/run/report.html`; откройте его
в браузере. Это живые детекторы на искусственном наборе, а не оценка скрытого теста.
`npm run demo` остаётся старым воспроизведением заранее подготовленных находок.

На объединённой сборке 31.10.2026: 285 тестов успешно, 0 ошибок, 2 пропуска
(создание символических ссылок недоступно в проверенной Windows-среде).
Проверки контрактов, всех командных модулей, Flutter и упаковки пройдены,
в том числе из распакованного архива кода. На GitHub прошли все пять заданий:
Windows/Linux с Node 22/24 и отдельный Flutter-прогон
([подтверждённый запуск сборки](https://github.com/foxfordkz-cyber/stupits-karaganda/actions/runs/41220505279)).
Счётчики выше относятся к локальной Windows; на CI доступность символических
ссылок может отличаться. История следующих запусков доступна во вкладке Actions.

## Проверка своих ARB

```sh
node scripts/run-pipeline.mjs --config contracts/examples/pipeline.json --source /private/intl_ru.arb --target /private/intl_kk.arb --glossary modules/linguistics/glossary.csv --combine-same-text --out ../locqa-private/analysis-001
```

Замените `/private/...` действительными путями. Выход должен быть новым и находиться
**вне любого Git checkout**. Предоставленный глоссарий — черновик, не одобрение носителя.
Без `--reviews` выполняется анализ: создаются report.json, report.html, bundle,
служебные отчёты модулей и pipeline-evidence.json. Исходные ARB не меняются.
Модельный API не вызывается: стандартный командный маршрут использует local_only.

`--combine-same-text` явно объединяет несколько машинных наблюдений одного типа
на точной паре source/target. Все объяснения и варианты остаются в отчёте и
merge-audit.json. Разные предложения не выбираются автоматически: suggestion
остаётся пустым. Разные версии текста и неоднозначные дубли этим не разрешаются.
Без опции действует прежний строгий отказ при конфликте. [Подробности pipeline](docs/PIPELINE.md).

Для отдельной технической проверки доступна команда Core:

```sh
node modules/core/cli.mjs check --source /private/intl_ru.arb --target /private/intl_kk.arb --glossary modules/linguistics/glossary.csv --out ../locqa-private/core-001
```

На Windows тот же интерфейс запускается через `modules\core\locqa.cmd check`.
Полный командный анализ с языковыми правилами выполняет `scripts/run-pipeline.mjs` выше.

## Что получает проверяющий

| Файл / материал | Содержимое |
|---|---|
| `bundle.json` | Ключи и конкретные вхождения, исходный и целевой тексты, контекст, хэши версий |
| `core-report.json`, `language-report.json` | Отдельные результаты владельцев модулей |
| `report.json` | Общие находки с полями `key`, `issue_type`, `severity`, `source`, `target`, `evidence`, `suggestion`, `confidence`, `reviewed_by_human` |
| `report.html` | Автономный отчёт и интерфейс для просмотра и рабочих правок |
| `*.diagnostics.json`, `merge-audit.json` | Структурные проблемы и сохранённые варианты объединённых наблюдений |
| `language-report.json.details/` | Очередь v2, привязки находок к версиям, предложения и метрики обработки |
| `pipeline-evidence.json` | Параметры этапов, коды завершения, хэши входов и выходов, состояние экспорта |
| `modules/linguistics/glossary.csv` | 40 черновых терминов в формате `ru,kk,en,comment` |
| Журнал `reviews` | Точные решения реального проверяющего; без проверки остаётся пустым |
| `intl_kk_fixed.arb` | Выход защищённого экспорта при выполненных условиях; обычный анализ его не создаёт |

Официальная находка не содержит вхождение ключа, поэтому привязки хранятся отдельно.
Очередь Language v2 относится к отдельному языковому отчёту; интерфейс Тони работает
с общими bundle/report. Эти представления не следует считать взаимозаменяемыми.

## Редактор, человеческие решения и экспорт

В report.html доступны поиск, фильтры, рабочие правки, сохранение сессии и отчёт
для эксперта. Кнопки интерфейса сохраняют черновики. Официальный reviews содержит
только отдельно импортированные применимые человеческие решения; без них он пуст.
Для реальных решений нужны точный проверенный текст, автор, дата и хэши версий.

После согласования исходной структуры и получения настоящего журнала:

```sh
node modules/core/cli.mjs export --source /private/intl_ru.arb --target /private/intl_kk.arb --reviews /private/reviews.json --out ../locqa-private/approved-001 --verify-flutter
```

Конфликтующие target-дубли требуют дополнительного `--resolutions`.
Старые решения после изменения source/original/approved не применяются.
Не подменяйте исходный baseline машинным кандидатом ради прохождения проверки.
Финальный архив переводов собирается только через [проверяемую упаковку](docs/PACKAGING.md).

## Материалы и ограничения

Для передачи всей командной работы подготовлены архив кода, общий README,
журналы проверок и отдельный закрытый рабочий пакет. Архив кода содержит только
отслеживаемые исходники и придуманные примеры. Закрытый пакет содержит реальный
отчёт и машинные предложения и имеет явный статус `HUMAN_REVIEW_PENDING`.

При показе жюри можно пройти четыре шага: запустить `npm run verify-team`, открыть
созданный HTML, показать объяснение находки и сохранение рабочей сессии, затем
показать журналы Flutter и блокировку неодобренного изменения. Реальный исправленный
перевод без завершённой проверки носителем не заявляется как готовый результат.

| Область | Инструкция |
|---|---|
| Ядро, пять технических проверок, CLI | [Core](modules/core/README.md) |
| Языковые правила, бюджеты, ограничения | [Language](modules/language/README.md) |
| Версионные очереди и проверка решений | [Review gate](modules/language/REVIEW_GATE.md) |
| Черновой глоссарий и аудит носителя | [Linguistics](modules/linguistics/README.md) |
| HTML и восстановление рабочей сессии | [Report](modules/report/README.md) |
| Общие форматы | [Contracts](docs/CONTRACTS.md) |
| Методология и человеческая оценка | [Методология](docs/METHODOLOGY.md), [оценка](docs/HUMAN_EVALUATION.md) |
| Состав финальной сдачи | [Submission](docs/SUBMISSION.md), [Packaging](docs/PACKAGING.md) |

Языковые эвристики и длина требуют проверки в контексте; precision/recall скрытого
набора неизвестны. Глоссарий пока черновой. Очередь Language v2 сохраняется отдельным
файлом; HTML использует общий bundle/report. Неоднозначные вхождения требуют выбора.
Качество языка, реальные размеры интерфейса игры и обращения к переименованным
ключам не подтверждаются успешным Flutter gen-l10n.

Исходные выгрузки, производные отчёты, реальные журналы и технический ARB-кандидат
не входят в публичный Git или архив кода. Для них подготовлен отдельный приватный
рабочий пакет с явной отметкой «не финальная сдача». Он не содержит созданных ИИ
человеческих одобрений и не выдаётся за проверенный intl_kk_fixed.arb.
