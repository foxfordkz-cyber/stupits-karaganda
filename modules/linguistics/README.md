# Глоссарий и проверка — Айдана / назначенный носитель

Модуль содержит [40 черновых терминов](glossary.csv) в командном формате
`ru,kk,en,comment`, [редакторскую политику](POLICY.md), очередь кандидатов и аудит
человеческих решений. Проверенных носителем строк в этой передаче **0**.
Исходная раздатка и реальные кандидаты не предоставлены; используются общие
синтетические примеры. [Разбор их предложений](CANDIDATE_NOTES.md) также не является
человеческим одобрением.

## Запуск

Node.js 22+, команды из корня репозитория. Зависимости уже указаны в корневом
lock-файле, новых пакетов нет. После `npm ci`:

```sh
node modules/linguistics/cli.mjs --help
node modules/linguistics/cli.mjs prepare --bundle outputs/bundle.json --report outputs/report.json --out private/linguistics/run-001 --batch-size 25
```

`bundle` и `report` соответствуют [общему контракту](../../docs/CONTRACTS.md).
Скрипт не читает и не переписывает исходные ARB. Каталог `--out` должен быть новым
и находиться внутри `private/`, `outputs/` или `submission/` этого репозитория.
Существующие результаты не перезаписываются, пути через внешние ссылки отклоняются.

Полный демонстрационный прогон на **подготовленных синтетических находках**
в PowerShell, без запуска детектора:

```powershell
New-Item -ItemType Directory -Path private/linguistics/demo-001
node fixtures/synthetic/adapters/adapter.mjs normalize --source fixtures/synthetic/source.arb --target fixtures/synthetic/target.arb --out private/linguistics/demo-001/bundle.json
node modules/linguistics/cli.mjs prepare --bundle private/linguistics/demo-001/bundle.json --report fixtures/synthetic/report.sample.json --out private/linguistics/demo-001/queue
node modules/linguistics/cli.mjs audit --bundle private/linguistics/demo-001/bundle.json --reviews private/linguistics/demo-001/queue/reviews.json --out private/linguistics/demo-001/audit
```

Получаются 11 записей, один неполный пакет, 40 черновых терминов и пустой `reviews`.
`Audit: empty` означает отсутствие решений, а не готовность исправлений к выпуску.
Повторный запуск выполнять с новым номером каталога.

## Выходы и работа человека

| Файл | Назначение |
|---|---|
| `queue.csv` | Простая таблица: исходник, KK, все варианты, причины, поля заметок |
| `batch-001.json` и далее | Точные тексты, контекст, хэши и техническая диагностика, 20–30 строк на пакет |
| `batch-001.md` и далее | Тот же пакет для последовательного чтения и ручных заметок |
| `bundle.snapshot.json`, `report.snapshot.json` | Снимки входов для истории |
| `glossary.snapshot.csv`, `term-decisions.jsonl` | Версия словаря и 40 незавершённых терминологических решений |
| `term-review.md` | Все 40 терминов с пустыми полями для согласования вариантов и исключений |
| `annotations.snapshot.json` | Редакторские заметки, если передан `--annotations`; исходные предложения сохранены |
| `reviews.json` | Пустой журнал завершённых решений по общей схеме |
| `manifest.json` | Число строк, пакетов, терминов и хэши входов |

CSV — удобное представление для заметок, не формат импорта одобрений. Открывать
как UTF-8 с разделителем «запятая» и текстовыми столбцами. Значения, похожие на
формулы, экранируются апострофом только в CSV. `null` и пустая строка различаются
в JSON; JSON сохраняет точный текст, переносы и технические токены.

1. Назначить пакет реальному носителю; `assigned_reviewer` изначально null.
2. Сопоставить исходник, KK и все предложения. Проверить контекст по POLICY.md.
   `final_text`, `changed_by`, `rationale` в рабочем JSON можно использовать для
   черновой правки. Ни одно рабочее поле не превращается автоматически в одобрение.
3. После чтения финального текста человек создаёт запись в `reviews.json` по
   общему контракту: `key`, `entry_id`, `decision`, `original_text`, `approved_text`,
   три хэша, `reviewer`, `reviewed_at`, `reviewed_by_human`. Запись `accepted` означает
   принятие предложения, `edited` — собственную правку, `rejected` — отклонение.
   Для отклонения approved-поля null. Для отсутствующего перевода original-поля null.
   Рабочие поля, причины и автор правки остаются в пакете, не добавляются к схеме.
4. Хэши source/original уже есть в пакете. SHA-256 финального текста можно получить
   через общий `hashText` или `node modules/linguistics/cli.mjs hash --text-file private/final-text.txt`.
   Команда учитывает **все** символы файла, включая BOM и последний перевод строки:
   содержимое файла должно точно совпадать с `approved_text`. Хэш не является подписью человека.
5. Сохранить новый снимок после каждой правки, причину и автора в рабочем журнале.
   Для повторного одобрения требуется новое чтение, а не исправление старых хэшей.
   Не хранить несколько текущих решений для одного `entry_id` в одном `reviews`.
6. Проверить актуальность решения относительно **текущего** bundle:

```sh
node modules/linguistics/cli.mjs audit --bundle outputs/bundle.json --reviews private/linguistics/run-001/reviews.json --out private/linguistics/audit-001
```

Аудит сохраняет точный снимок переданных решений и список проверок. Он не выставляет
флаг человека и не изменяет `reviews`. `consistent` подтверждает только схемы,
идентификаторы, хэши и перечисленные технические ограничения. Применение решения
и экспорт ARB выполняет ядро; финальные проверки и Flutter — интегратор.

Несколько находок одного ключа сохраняются в одной записи. Разные предложения
одной пары ключ/тип, устаревшие входные тексты и неоднозначные вхождения ключа
блокируют создание очереди. Нельзя выбирать один из дублей молча. Второму носителю
передают отдельный пакет; вручную заполненные журналы объединяют с контролем
уникальности `entry_id` и последующим аудитом.

## Проверки и ограничения

```sh
node --test modules/linguistics/workflow.test.mjs
npm test
npm run check
```

Тесты покрывают совместимость контрактов, пустые одобрения, сохранение вариантов,
пакеты без повторов, устаревшие хэши, отсутствующий перевод, конфликтующие дубли,
защиту исходников, ICU/printf/теги, служебные значки и CSV-экранирование.
Все тестовые одобрения существуют только в памяти и помечены SYNTHETIC TEST ONLY.

Это не морфологический анализатор и не детектор ошибок; автоматической замены
глоссария нет. Качество языка, естественность, смысл всех ICU-ветвей и игровой
рендеринг проверяет человек. Проверка подписей плейсхолдеров использует общий
`technicalSignature`, не доказывает сохранение их роли в предложении и кратности
каждого использования. Изменение числа переносов даёт предупреждение.
Аудит не удостоверяет личность редактора и не доказывает, что текст был прочитан.
Без реального носителя нельзя объявлять требования к человеческой проверке выполненными.

## Редакторские варианты до человеческой проверки

[TERM_DECISIONS.md](TERM_DECISIONS.md) содержит 12 спорных групп терминов с
конкретными вариантами и вопросами. В [CANDIDATE_NOTES.md](CANDIDATE_NOTES.md)
зафиксированы 11 точных синтетических вариантов; в двух уточнена формулировка модели.

Для собственных данных можно передать `--annotations private/notes.json` вместе
с обычной командой `prepare`. Формат локален для модуля, общие схемы не меняются:

```text
workflow_version: "1.0"
target_locale: та же локаль, что у bundle
annotations: массив объектов со строго следующими полями:
  entry_id: идентификатор из пакета
  source_hash: точный source_hash из пакета
  original_hash: точный original_hash из пакета, включая null
  proposed_text: новый вариант либо null, если пока есть только вопрос
  author: автор редакторской заметки, например "AI draft"
  rationale: причина выбора или изменения
  questions: массив ещё не решённых вопросов, может быть пустым
```

Неполные записи, посторонние поля, устаревшие хэши и повторные заметки одного
`entry_id` отклоняются до записи выходов. `author` не является `reviewer`.
Редакторский вариант получает собственный хэш и техническую диагностику,
но статус остаётся `pending_human_review`, `reviews.decisions` остаётся пустым.
Неисправный технический вариант виден как `failed`; он не получает одобрения.
Оригинальные предложения модели остаются в JSON и в печатном пакете рядом с новым.

Для следующей редакции использовать новый каталог запуска и сохранить предыдущий.
Так остаётся история того, кто предложил вариант, почему он изменён и к каким
исходным текстам относится. Текст Markdown/CSV не импортируется как одобрение:
после чтения человек оформляет точную финальную версию по контракту `reviews`.

Границы передачи: только `modules/linguistics/`; общие схемы, зависимости,
исходные файлы и другие модули не изменяются. Реальные данные и журналы остаются
в игнорируемых каталогах. Ограничения в таблице терминов требуют решения носителя,
а не дополнительных исправлений ради количества.
