# Core & CLI — единая инструкция и передача работы Дамира

Здесь собраны запуск, возможности, форматы, результаты проверок, состояние соседних веток и ссылки на закрытые материалы. Это основной документ модуля Дамира; прежний HANDOFF ведёт сюда.

**Технический модуль готов к интеграции.** Он читает ARB без потери вхождений, выполняет пять проверок и экспортирует изменения по применимым человеческим решениям. Ветка — `codex/core-cli`, проверенная версия кода — `e216ac6`, база интегратора — `62fa3a8`. Код и тесты находятся только в `modules/core/`; общие схемы, зависимости и чужие модули не изменены.

**Реальная локализация ещё не готова к сдаче.** Технический кандидат прошёл Flutter, но остаются вопросы к исходной структуре, отсутствующие переводы, проверка обращений игрового клиента и настоящие решения человека. Успех генерации не означает одобрение переводов.

## Запуск

Требуются Node.js 22 или новее, зависимости из корневого lock-файла и Flutter SDK в `PATH` для проверки генерации. На новом компьютере один раз выполните `npm ci` из корня репозитория. Python нужен языковому модулю Бекзата; самому ядру он не требуется.

На Windows для полной технической проверки достаточно одной команды. Она работает **из любой папки**, включая `C:\Users\...`:

```bat
C:\stupits-karaganda\modules\core\verify.cmd
```

Если репозиторий находится в другом месте, укажите его полный путь. Скрипт сам находит корень проекта, выполняет `npm test`, `npm run check` и настоящий Flutter-прогон экспорта. В консоли показаны `RUN/PASS/FAIL`; подробные логи и `verification.json` сохраняются в новом игнорируемом `outputs/core-verification-*`. Преднамеренные отказы Flutter в отрицательных тестах остаются в логах. Проверка использует искусственные данные, не создаёт реальных человеческих одобрений и не означает готовность реальных переводов к сдаче.

Без Windows-обёртки можно запускать тот же сценарий полным путём:

```bat
node C:\stupits-karaganda\modules\core\scripts\verify.mjs
```

Для обычных команд с относительными путями сначала перейдите в проект. В **CMD**:

```bat
cd /d C:\stupits-karaganda
```

В **PowerShell**: `Set-Location C:\stupits-karaganda`. Ошибка `Cannot find module C:\Users\...\modules\...` означает, что относительную команду запустили из другой папки; воспользуйтесь полным путём выше.

Из корня репозитория, без установки глобального пакета:

```powershell
.\modules\core\locqa.cmd check --source fixtures/synthetic/source.arb --target fixtures/synthetic/target.arb --glossary fixtures/synthetic/glossary.csv --out outputs/core-demo
```

Это настоящий детектор на вымышленных данных с намеренно внесёнными ошибками. Для проверки своих файлов укажите их пути:

```powershell
.\modules\core\locqa.cmd check --source data/intl_ru.arb --target data/intl_kk.arb --glossary private/glossary.csv --out outputs/core-new-run
```

Пути `data/intl_ru.arb`, `data/intl_kk.arb` и `private/glossary.csv` — пример размещения входов, а не поставляемые с Git файлы. Можно передать абсолютные пути к оригиналам вне репозитория; копировать или изменять оригиналы для анализа не требуется. Если реального глоссария пока нет, допустим CSV только с заголовком `ru,kk`, но в отчёте не будет исключений для неизменяемых терминов.

Чтобы использовать точную команду из брифа в текущем PowerShell:

```powershell
$env:Path = (Resolve-Path .\modules\core).Path + [IO.Path]::PathSeparator + $env:Path
locqa check --source fixtures/synthetic/source.arb --target fixtures/synthetic/target.arb --glossary fixtures/synthetic/glossary.csv --out outputs/core-demo-2
```

На Linux/macOS: `modules/core/locqa check ...`. Универсальный вариант: `node modules/core/cli.mjs check ...`. Если `@@locale` отсутствует, добавьте `--source-locale ru --target-locale kk`. Явная локаль не может противоречить существующей метке.

`--out` — **новый каталог**. Каждый запуск требует отдельного имени: существующие каталоги и входные файлы не перезаписываются. Внутри репозитория разрешены только подкаталоги игнорируемых `outputs/`, `private/`, `data/`, `submission/`; проверяются также ссылки на каталоги. Проверка чтения UTF-8 строгая, без замены повреждённых байтов.

Коды завершения: `0` — чистая проверка/успешный экспорт; `1` — найдены конкурсные проблемы; `2` — структурные проблемы, ошибка входных данных или заблокированный экспорт. Синтетический сломанный пример ожидаемо возвращает `1`.

## Общие форматы

Источник истины — [контракты команды](../../docs/CONTRACTS.md) и схемы в [contracts/](../../contracts/). Ядро не вводит свой несовместимый формат.

| Формат | Содержание и привязка версии |
|---|---|
| `bundle` — записи локализации | Локали, `key`, `entry_id`, `occurrence`, исходный и целевой текст, `context`, точные SHA-256. Отсутствующий перевод: `target=null`, `occurrence=0` |
| `report` — находки | Ровно `key`, `issue_type`, `severity`, `source`, `target`, `evidence`, `suggestion`, `confidence`, `reviewed_by_human`; у машинных находок последнее поле `false` |
| `reviews` — решения человека | Ключ/вхождение, `accepted`/`edited`/`rejected`, первоначальный и одобренный текст, проверивший, время и хэши source/original/approved |

Изменение любого из трёх текстов делает одобрение неприменимым. ИИ не создаёт реальные `reviewed_by_human=true`. Трассировка вхождений, дубли и ошибки структуры хранятся отдельно от конкурсных типов. Повторный `@@comment` сохраняется как разделитель.

## Результаты проверки

| Файл | Содержание |
|---|---|
| `bundle.json` | Общий контракт v1, точные SHA-256 текстов, вхождения, разделы и описания |
| `report.json` | Только девять согласованных полей; пять типов ядра; все `reviewed_by_human=false` |
| `trace.json` | Индекс находки в report и связанные `entry_id`; одинаковые находки объединены без потери вхождений |
| `diagnostics.json` | Дубли, структура/имена ключей, некорректный исходный ICU, технические символы, лишние целевые ключи |
| `audit.json` | Хэши файлов, все свойства в порядке входа, сырые фрагменты, позиции UTF-16 и номера строк/колонок с 1 |
| `baseline-plan.json` | Черновик структурных решений для интегратора: хэши исходных файлов, все вхождения/разделы, одинаковые и конфликтующие дубли, недопустимые имена; `decision: null` |
| `manifest.json` | Режим `live_core_detection`, версии Node/ICU, параметры длины, числа находок и структурных ошибок |
| `failure.json` | Причина аварийного завершения после резервирования выходного каталога |

Эти файлы содержат производные данные и должны оставаться вне Git. `audit.json` сохраняет в том числе все повторные `@@comment` и метаданные; целевые ключи без источника не попадают в парный bundle. При конфликтующих исходных дублях записи этого ключа исключаются из bundle до согласованного выбора исходного значения. Обычные целевые дубли сохраняют отдельные `entry_id`.

`baseline-plan.json` — служебная диагностика модуля, а не новый общий контракт или журнал человеческой проверки. Он не выбирает значения и не применяется автоматически. Для одинаковых дублей `requires_integrator_decision=false`: экспортер может убрать их с сохранением эффективного текста и аудитом. Для конфликтов и остальных дефектов нужно явное решение. Пустые или некорректные Unicode-ключи остаются в диагностике и аудите, не прерывая анализ остальных записей.

Правила:

- `untranslated`: отсутствующий, пустой или состоящий из пробелов перевод непустого источника; отсутствие отличается от пустой строки.
- `same_as_source`: точное совпадение текста, включая текст внутри вложенных ICU-ветвей. Числа, символы и сообщения только из ICU-переменных, тегов, printf или сущностей исключены. Допустимые неизменные слова/бренды берутся из одинаковых RU/KK значений CSV, с сопоставлением регистра. Имена и другие бренды без записи в глоссарии могут дать ложные срабатывания.
- `placeholder_mismatch`: имена и типы ICU-аргументов, select-ветви, форматирование чисел/дат, printf-параметры и теги. Проверяются повторные вхождения форматированных аргументов, вложенность и техническое содержимое каждой ветви: одинаковое общее количество тегов или printf не скрывает их перенос в другую ветвь.
- `plural_mismatch`: синтаксис, обязательная `other`, вид cardinal/ordinal, offset, точные `=N`-ветви и вложенная структура. Категории берутся из CLDR через `Intl.PluralRules` целевой локали. RU `few/many` не требуются в KK. Отсутствующие необязательные категории используют `other`; неиспользуемые в данной локали категории отмечаются отдельно в объяснении.
- `length_overflow`: число видимых графем >2× источника, источник не длиннее 20 графем, цель не короче 10. Настройки: `--length-ratio`, `--short-limit`, `--length-minimum`. В ICU берётся самая длинная ветвь, ширина подстановок неизвестна.

Глоссарий: CSV с колонками локалей (например `ru,kk,en,comment`), поддерживаются кавычки, запятые и переносы внутри полей. Ядро использует только исключения совпадающих терминов; проверка `glossary_violation` принадлежит языковому модулю. CSV только с заголовком допустим, но исключений у него нет. Автоматические исправления не предлагаются: `suggestion` остаётся пустым.

## Экспорт

Команда ниже предназначена для новой выдачи после получения настоящего `reviews.json`. В `--target` укажите согласованный исходный файл; не подменяйте его машинным черновиком из закрытого каталога.

```powershell
.\modules\core\locqa.cmd export --source data/intl_ru.arb --target data/intl_kk.arb --reviews private/reviews.json --source-locale ru --target-locale kk --out submission/core-approved --verify-flutter
```

Результат — `intl_kk_fixed.arb` (имя зависит от целевой локали) и `export-audit.json`. Экспорт:

- Валидирует общий контракт reviews, локаль, `entry_id`, исходный текст и все три хэша. Изменение источника, первоначального перевода или одобренной версии блокирует устаревшее решение. Флаг в report не используется как разрешение на исправление.
- Применяет только `accepted`/`edited`, сохраняет неизменённые значения, повторные разделители и существующие метаданные. Для добавляемого перевода копирует доступные исходные метаданные без прежней отметки проверки.
- Переносит шесть полей `@key.x-locqa` из предоставленного решения. Неподтверждаемые прежние `true`-метки удаляются с записью в аудит; ложные/тестовые метки не повышаются до `true`. Производственного метода создания одобрения нет.
- Проверяет ICU, printf, теги, переносы/табы, private-use и format-символы, символы категории Unicode `S`, вариационные селекторы, сущности, обратные слеши, экранированные фигурные скобки, `%%` и удвоенные ICU-апострофы. Нельзя удалить дополнительный защищённый символ исходного target даже при исправлении повреждённого ICU.
- Убирает одинаковые целевые дубли с сохранением последнего эффективного значения и всех вхождений/разделов в `duplicate_audit`. Исходный source не переписывается. Конфликтующие source-дубли и дубли атрибутов блокируют экспорт.
- При конфликтующих target-дублях принимает `--resolutions private/duplicate-resolutions.json` по общему [контракту интегратора](../../docs/DUPLICATES.md). Проверяет хэши обоих исходных файлов, вхождение и выбранный текст через `verifyResolutions`. Выбор более раннего значения, меняющий действующий текст, требует ещё и reviews: его `original_text` и `entry_id` привязаны к последнему исходному вхождению, как требует независимый release gate. Ни решений по дублям, ни одобрений экспортер не создаёт.
- Повторно выполняет независимый `checkRelease` интегратора перед записью. Все проверки проходят до создания итогового ARB. Пустой журнал не меняет переводы.

С `--verify-flutter` CLI сохраняет точные копии source и кандидата в `flutter-inputs/`, запускает существующий Flutter-runner интегратора в `flutter/`, сверяет хэши, коды завершения всех трёх команд и наличие сгенерированного Dart. Только после успеха появляется итоговый `intl_kk_fixed.arb`. При ошибке остаются диагностические копии, журнал и `failure.json`, но итогового ARB нет. В `export-audit.json` сохраняются `flutter_verified: true` и доказательство для точной пары; вложенный `release` по-прежнему описывает только независимую предварительную проверку.

Без флага сохраняется прежний режим экспорта с `flutter_verified: false`, требующий отдельного Flutter-прогона. `export --help` и `check --help` показывают параметры без чтения файлов.

API для интегратора экспортируется из `modules/core/index.mjs`: `readArb(text, side)`, `normalizeArbs({sourceText, targetText, sourceLocale?, targetLocale?})`, `checkArbs({sourceText, targetText, glossaryText?, sourceLocale?, targetLocale?, lengthRatio?, shortLimit?, lengthMinimum?})`, `checkBundle(bundle, options)`, `exportApproved({sourceText, targetText, reviews, resolutions?, sourceLocale?, targetLocale?})`. `checkArbs` возвращает объекты перечисленных файлов (для `baseline-plan.json` свойство называется `baselinePlan`), `exportApproved` — `{text, audit}` без записи на диск и без запуска Flutter. За приватное место хранения при прямом использовании API отвечает вызывающий код.

## Подключение к общему маршруту

Реализованы точные интерфейсы `contracts/examples/pipeline.json`, без изменения конфигурации или кода интегратора:

```powershell
node modules/core/normalize.mjs --source data/intl_ru.arb --target data/intl_kk.arb --out outputs/run/bundle.json
node modules/core/check.mjs --bundle outputs/run/bundle.json --glossary private/glossary.csv --out outputs/run/core-report.json
node modules/core/export.mjs --source data/intl_ru.arb --target data/intl_kk.arb --reviews private/reviews.json --out outputs/run/intl_fixed.arb
```

У адаптеров `--out` — новый **файл**, у `locqa` — новый **каталог**. Все выходы защищены от перезаписи и записи в публичную часть репозитория. Адаптеры создают рядом служебные `.audit.json`, `.diagnostics.json`, `.trace.json` или `.baseline-plan.json`. Код `0` адаптера означает, что корректный артефакт сформирован, даже когда report содержит находки; ошибки завершаются кодом `2`. Файловый export принимает необязательный `--resolutions` и оставляет Flutter-проверку общему упаковщику. Для самостоятельного выпуска используйте `locqa export --verify-flutter`.

Если в ARB нет `@@locale`, в argv нормализатора/экспортера явно добавляются `--source-locale` и `--target-locale`; локали не угадываются. Конфликтующий source не нормализуется с молчаливым выбором строки. Языковой модуль и HTML-интерфейс остаются стадиями соответствующих владельцев; их тестовые замены явно обозначены в тесте общего маршрута.

Проверенная связка на синтетике: **реальные normalize/core → локальный детектор Бекзата → общий merge → тестовый render**, затем настоящие prepare/audit Айданы. Render обозначен как заглушка: готового модуля Тони в проверенных ветках нет. Пакеты Айданы содержат пустой журнал решений и не означают человеческую проверку.

Слияние веток и окончательную настройку [pipeline](../../docs/PIPELINE.md) выполняет интегратор. Адаптер Бекзата требует хранить выходы **вне любого Git checkout**, поэтому общий маршрут после его подключения должен получать внешний приватный `--out`. Примеры `outputs/run/...` выше относятся к отдельным адаптерам ядра. Проверка слияния с опубликованными ветками Айданы и Бекзата не выявила текстовых конфликтов; сами ветки здесь не объединялись.

Тестовые одобрения не являются человеческой проверкой; реальные файлы скрипт не читает. Логи и результаты сохраняются только в новом `outputs/core-flutter-test-*`.

## Оставшиеся шаги команды

По реализации Core & CLI незакрытых задач в этой передаче нет. Для общей сдачи остаются действия владельцев:

1. Интегратор согласует исходную структуру, неоднозначные дубли и имена ресурсов, сохранив оригиналы, их хэши и документированное соответствие. Изменённые имена сверяются с обращениями игрового клиента.
2. Проверяющий читает конкретные версии переводов и оформляет настоящие решения по общему контракту. Отсутствующие переводы также требуют проверки; доверие к ИИ не является чтением точной версии.
3. Бекзат устраняет описанный сбой проверки вложенности; Тони предоставляет интерфейс. Интегратор объединяет модули и повторно проверяет общий маршрут.
4. На согласованных исходниках ядро выполняет `export --verify-flutter` с применимыми решениями. Интегратор запускает независимую проверку и [упаковку](../../docs/PACKAGING.md) точного результата.

Нельзя обходить блокировку выпуска, заменяя первоначальные входы очищенным кандидатом без согласованного аудита. Итоговый ARB создаётся только после успешных проверок предоставленных решений и технической сохранности.

## Известные ограничения

ICU-парсер поддерживает больше конструкций, чем Flutter; реальный прогон через `--verify-flutter` или отдельный smoke-test остаётся обязательным. Ширина виджетов, качество казахского текста и личность проверяющего не устанавливаются. `confidence` не калибрована как вероятность. Сохранение технических символов консервативно: изменение их количества между plural-ветвями или конфликтный baseline может потребовать ручного согласования. Отсутствующие переводы без одобрения остаются отсутствующими и отмечаются независимой проверкой; генерация с fallback не доказывает полноту локализации.

Ориентиры: [Flutter internationalization](https://docs.flutter.dev/ui/internationalization), [Unicode CLDR plural rules](https://cldr.unicode.org/index/cldr-spec/plural-rules). Общие контракты: [CONTRACTS.md](../../docs/CONTRACTS.md).
